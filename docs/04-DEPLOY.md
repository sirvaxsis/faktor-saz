# ۰۴ — استقرار (میزبانی، آدرس‌ها، به‌روزرسانی)

## ۱) میزبانی: GitHub Pages برای فروش اشتراک مناسب نیست
طبق شرایط/محدودیت‌های GitHub Pages (به‌شکلی که من می‌شناسم؛ متن فعلی را خودتان در مستندات GitHub بخوانید)، Pages برای «اجرای کسب‌وکار آنلاین / سایتی که عمدتاً برای معاملات تجاری یا ارائهٔ نرم‌افزار تجاری به‌صورت سرویس (SaaS) است» در نظر گرفته نشده. یک فاکتورساز اشتراکی پولی در همین دسته می‌افتد. ریسک: تعلیق سایت یا ریپو بدون هشدار.

**پیشنهاد:** فرانت‌اند را روی **Cloudflare Pages** (پلن رایگان؛ استفادهٔ تجاری مجاز است — شرایط فعلی را تأیید کنید) میزبانی کنید. جایگزین‌ها: Netlify (پلن رایگان). از **Vercel Hobby** استفاده نکنید (پلن Hobby برای استفادهٔ غیرتجاری است). هیچ دامنهٔ خریداری‌شده‌ای لازم نیست؛ آدرس `https://<نام>.pages.dev` کافی است.

**Cloudflare Pages (بدون بیلد):**
1. مخزن (می‌تواند Private باشد) را در GitHub بسازید و **فقط پوشهٔ `site/`** را در آن بگذارید (یا کل پروژه را بگذارید و Build output را `site` تعیین کنید).
2. Cloudflare → Workers & Pages → Create → Pages → Connect to Git.
3. Framework preset: *None*. Build command: خالی. Build output directory: `site` (یا `/` اگر فقط محتوای site را در ریشه گذاشته‌اید).
4. بعد از دیپلوی، آدرس `*.pages.dev` را بردارید. فایل `site/_headers` (هدرهای امنیتی و `no-cache` برای `sw.js` و `cloud-config.js`) خودکار اعمال می‌شود.

> ⚠️ دسترسی از ایران: من نتوانستم دسترسی‌پذیری `supabase.co` و `pages.dev` را از شبکه‌های ایران آزمایش کنم. پیش از راه‌اندازی تجاری، از چند اینترنت واقعی (همراه اول، ایرانسل، ADSL) هر دو آدرس را باز کنید. اگر فیلتر بود، یک دامنهٔ اختصاصی روی Cloudflare (یا پراکسی) لازم می‌شود.

## ۲) آدرس نهایی را همین حالا تثبیت کنید
مرورگر داده‌های محلی را «به‌ازای آدرس» جدا نگه می‌دارد. اگر آدرس را بعداً عوض کنید، کاربرانِ بدون حساب داده‌هایشان را در آدرس جدید نمی‌بینند. (کاربران دارای حساب مشکلی ندارند: داده روی سرور است.) پس قبل از مشتری واقعی آدرس را قطعی کنید و در *Site URL* و *Redirect URLs* Supabase بگذارید.

## ۳) آدرس‌های بازگشت (Supabase → Authentication → URL Configuration)
- Site URL: `https://<آدرس نهایی>/`
- Redirect URLs: `https://<آدرس نهایی>/` ، `https://<آدرس نهایی>/index.html` (و برای آزمایش محلی `http://localhost:8765/`)
- لینک ایمیل تأیید و بازیابی رمز با `#access_token=…&type=signup|recovery` به همین صفحه برمی‌گردد؛ `cloud.js` آن را می‌خواند، نشست را ذخیره می‌کند و فوراً hash را از آدرس پاک می‌کند. (`type=recovery` پنجرهٔ «تعیین رمز جدید» را باز می‌کند.)
- اگر کاربر لینک منقضی را باز کند، پیام «لینک نامعتبر یا منقضی است» نشان داده می‌شود.

## ۴) Service Worker و کش
- `sw.js` فقط فایل‌های همین سایت و فونت‌ها را کش می‌کند. API و احراز هویت Supabase (مبدأ دیگر) از سرویس‌ورکر عبور نمی‌کنند و هرگز کش نمی‌شوند؛ یعنی داده یک کاربر برای کاربر دیگر نمایش داده نمی‌شود. (آزمون `15b`)
- کش هر صفحه با آدرس خودش است (اصلاح باگ قبلی که همهٔ ناوبری‌ها را روی `index.html` می‌نوشت).
- **هر بار فایل‌ها را منتشر کردید، `VERSION` در `sw.js` را بالا ببرید** (الان `v14-cloud`). نسخهٔ قدیمی کش خودکار پاک می‌شود.
- مسیر پایه: همهٔ آدرس‌ها نسبی‌اند (`./`) و در زیرمسیر (مثل `/factorsaz/`) هم کار می‌کنند.
- آفلاین: صفحه و فاکتورهای کش‌شده باز می‌شوند و PDF گرفتن از آن‌ها ممکن است؛ **ساخت/ذخیرهٔ فاکتور به اینترنت نیاز دارد** (سهمیه در سرور است). ویرایش‌های کوچک (وضعیت پرداخت، یادآوری، حذف) در صف می‌مانند و با برگشت اینترنت ارسال می‌شوند.

## ۵) فایل‌هایی که نباید بیرون بروند
`license-generator.html` و هر فایل کلید خصوصی (`PRIVATE-license-key-*.json`) فقط روی کامپیوتر شما بمانند. پوشهٔ `site/` را فقط منتشر کنید. آزمون خودکار تضمین می‌کند در `site/` اسرار (service_role، secret key، JWT، کلید خصوصی PEM) نباشد.
